# 편명으로 보는 공항 날씨와 옷차림

`PRODUCT.md` 성공 기준 1단계의 작업 단위입니다.

## 사용자 결과

승객이 출발 일자와 편명 하나를 입력하면, 출발 공항과 도착 공항 각각의 예정 시각 날씨예보와 그에 맞는 추천 옷이 한 화면에 표시됩니다.

승인된 화면은 [prototype.html](prototype.html)입니다. 화면 구성, 상태, 문구의 기준으로 삼되 더미 데이터와 동작은 구현 대상이 아닙니다.

## 범위

- 입력은 출발 일자(공항 현지 날짜, 왼쪽)와 편명 하나(오른쪽)이고, 제출 버튼 문구는 "조회하기"입니다. 좁은 화면에서는 날짜, 편명 순서로 쌓입니다.
- 결과가 나오면 입력 칸을 접고 조회 조건 요약(날짜 · 편명)과 "다시 조회" 버튼만 보여 줍니다. "다시 조회"를 누르면 입력 칸이 펼쳐집니다.
- 결과는 출발 공항과 도착 공항 두 곳을 같은 화면에 나란히(좁은 화면에서는 출발, 도착 순서로 쌓아서) 보여 줍니다.
- 각 공항 카드에는 공항 이름과 코드, 예정 시각(공항 현지 시각), 그 시각의 기온·체감 온도·강수 확률, 날씨 상태를 나타내는 아이콘과 이름, 추천 옷이 들어갑니다.
- 두 카드와 갈아입기 안내 아래에 "차이비교" 버튼을 두고, 처음에는 숨겨 둔 "공항 간 날씨 차이"를 이 버튼을 누르면 보여 줍니다. 날씨 상태 변화, 기온 차이, 강수 확률 차이(두 값을 겹친 막대와 차이 수치)를 항목별로 나타내고, 차이가 큰 항목은 강조합니다.
- 두 카드 바로 아래, 차이비교 버튼 위에 기내에서 갈아입는 방법을 안내하는 한 단락을 둡니다.
- 추천 옷은 겉옷과 기본 옷을 라벨로 구분하지 않고 아이콘이 붙은 옷 목록으로 표시하며, 우산 같은 지참 물품을 따로 표시합니다. 공항 옷에서 기내용으로 갈아입기 쉽게, 겉옷을 벗거나 입는 것으로 조절할 수 있는 구성을 우선합니다.
- 편명 데이터는 [편명 데이터 출처](../../decisions/flight-data-source.md) 결정에 따라 가져옵니다. 이 결정이 호출 방식, 키 관리, 출처 표기, 저장 기간을 정합니다.

## 범위 밖

- 환승편 입력과 여러 편명 처리(2단계), 귀국편(3단계).
- 재접속 시 이전 입력 재조회와 오프라인 저장본 표시. 이후 단계에서 다룹니다. 그때 편명 데이터 저장은 [편명 데이터 출처](../../decisions/flight-data-source.md)의 규칙(브라우저 저장소에 저장, 조회마다 새로 가져와 저장, 7일을 넘기지 않음)을 따릅니다. 이번 1단계에서는 저장하지 않습니다.
- 로그인, 계정, 서버 쪽 사용자 데이터 저장. 저장이 필요해지면 브라우저 저장소를 쓴다.

## 인수 기준

1. 실제 편명과 날짜(예: 오늘부터 며칠 뒤의 `KE17`)를 입력하면 출발 공항(ICN)과 도착 공항(LAX)의 카드가 모두 표시된다.
2. 각 카드의 시각은 해당 공항의 현지 시각이고, 두 공항의 시각이 서로 다른 시간대로 정확히 표시된다. 날짜가 바뀌는 도착도 도착 공항 현지 날짜로 표시된다.
3. 각 카드의 날씨는 그 공항 위치의 예정 시각에 가장 가까운 예보다. 두 공항의 날씨 값이 서로 다르게 표시될 수 있다.
3-1. 각 카드에 날씨 상태가 아이콘으로 표시되고, 두 공항의 상태가 다르면 아이콘도 다르다.
3-2. 두 공항의 날씨가 모두 있을 때만 "차이비교" 버튼이 나오고, 누르면 "공항 간 날씨 차이"가 표시된다. 날씨 상태 변화, 기온 차이(도착 기준 +/−), 강수 확률 차이(%p)가 실제 두 값에서 계산되어 표시되고, 상태가 바뀌거나 강수 확률 차이가 큰 항목은 다른 항목보다 강조된다. 한쪽 날씨가 없거나 예보가 없으면 이 영역은 표시되지 않는다.
4. 추천 옷은 같은 화면에서 날씨 조건에 따라 달라진다. 추운 날씨에는 따뜻한 구성, 더운 날씨에는 가벼운 구성이 나오고, 비 올 확률이 높으면 우산이 지참 물품에 나온다.
5. 빈 입력, 형식이 맞지 않는 편명, 날짜가 비어 있는 입력은 조회 없이 입력 칸에서 안내한다.
6. 존재하지 않거나 해당 날짜에 운항하지 않는 편명은 "찾을 수 없다"는 안내가 표시되고 빈 카드는 나오지 않는다.
7. 날씨 예보가 아직 제공되지 않는 먼 날짜(오늘부터 16일을 넘는 날짜)는 두 공항 카드와 예정 시각은 그대로 보여 주고, 날씨와 추천 옷 자리에 "아직 예보가 없습니다"라는 표시를 둔다. 예보가 열리는 시점이 되면 다시 조회하라는 안내를 함께 둔다. 이미 지난 날짜는 이유를 안내하고 날씨와 옷 추천을 보여 주지 않는다.
8. 조회 중에는 로딩 상태가 보이고, 편명 조회나 날씨 조회가 실패하면 오류 안내와 다시 시도하는 방법이 보인다. 한쪽 공항 날씨만 실패하면 성공한 쪽은 표시하고 실패한 쪽에 오류를 표시한다.
9. API 키는 브라우저로 전달되지 않는다. 네트워크 요청과 화면 어디에도 키가 나타나지 않는다.
10. 편명 데이터를 보여 주는 화면에 AeroDataBox 출처 표기가 있다.
11. 좁은 화면(약 400px)에서도 입력, 출발 카드, 도착 카드 순서로 쌓이고 내용이나 버튼이 숨지 않는다.

## 확정한 제약과 근거

- 편명 데이터 출처, 키 관리, 출처 표기, 저장 기간은 [편명 데이터 출처](../../decisions/flight-data-source.md)를 따른다.
- UI 구성은 [UI 구성 원칙](../../decisions/ui-composition.md)을 따른다. 로딩, 빈 상태, 오류, 성공 상태를 정상 화면과 같은 구성 문법으로 둔다.
- `PRODUCT.md`에서 가져오는 제약: 환승편의 기준은 실제 탑승 일시이고 귀국편만 별도 날짜를 입력한다(이번 범위에서는 적용되지 않음), 공항 옷에서 기내 옷으로 쉽게 갈아입을 수 있어야 한다.
- 편명 조회와 날씨 조회는 서버에서 수행한다. 키를 숨겨야 하고 같은 결과 형식을 화면이 받게 하기 위해서다.

## 가정(덮어쓸 수 있음)

- 기내 갈아입기 안내 문구는 두 공항의 겉옷과 날씨를 바탕으로 만든다. 구체적인 문장 규칙은 구현에서 정한다.
- "공항 간 날씨 차이"의 강조 기준(예: 강수 확률 차이 몇 %p부터)은 구현에서 정한다.
- 날씨 상태 아이콘의 종류는 날씨 코드를 묶어 구현에서 정한다(프로토타입은 맑음과 비 두 가지만 그렸다).
- 날씨 코드가 맑음, 구름 많음, 안개여도 강수 확률이 60% 이상이면 비 아이콘과 "비 올 가능성"으로 표시한다. 기준 60%는 바꿀 수 있다.
- 날짜 칸 아래의 "출발 공항 현지 날짜예요." 안내 문구는 두지 않는다.
- 날씨 데이터는 키가 필요 없는 Open-Meteo 시간별 예보를 쓴다. 이유는 가입 없이 실제 응답을 확인했고 16일 앞까지 예보를 주기 때문이다. 다른 출처를 원하면 바꿀 수 있다.
- "예정 시각의 날씨"는 예정 시각을 포함하는 정시 예보 한 시점으로 표시한다.
- 같은 편명이 한 날짜에 여러 건 응답되면 첫 번째 항목을 쓴다.
- 추천 옷은 기온과 체감 온도, 강수 확률, 날씨 상태로 정한 규칙으로 만든다. 구체적인 구간과 문구는 구현에서 정하고, 인수 기준 4의 방향만 지킨다.
- 도착 공항의 날씨 시각은 도착 예정 시각을 쓰고, 지연 예측 시각이 있어도 예정 시각을 쓴다.
- 입력한 날짜는 출발 공항 현지 날짜로 해석한다.

## 보류한 점

- 환승 편명 입력 방식과 여러 공항 표시(2단계).
- 귀국편 입력과 날짜 규칙(3단계).
- 이전 입력 저장과 오프라인 표시의 구체적 동작. 저장 기간과 갱신 규칙은 결정 문서로 정해져 있다.
- 서비스가 다루지 않을 범위(`PRODUCT.md`의 미정 항목).

## 남은 위험

- RapidAPI 무료 Basic의 월 한도가 작아 검증을 반복하면 소진될 수 있다. 소진되면 편명 조회가 거절되어 검증이 막힌다.
- 응답의 일정이 마켓플레이스 데이터의 "예상" 상태일 수 있고, 항공사가 일정을 바꾸면 실제와 달라질 수 있다.
- 편명 한 건이 여러 구간(경유 직항 등)이거나 한 날짜에 여러 건으로 응답되는 경우의 표시는 첫 항목 가정에 의존한다.
- 먼 미래 날짜는 일정은 응답되지만 날씨 예보는 16일 안쪽에서만 제공되어, 그 구간에서는 날씨와 옷 추천 없이 "아직 예보가 없습니다" 표시만 보인다(인수 기준 7).
